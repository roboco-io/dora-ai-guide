# 1. AIがアクセスできる社内データ

> 原文: <https://dora.dev/capabilities/ai-accessible-internal-data/>

## 定義

**AIがアクセスできる社内データ（AI-accessible internal data）** は、AIシステムを組織の独自情報 — コードベース、ドキュメント、運用指標 — に安全に接続し、**文脈を認識した応答**を可能にするケイパビリティです。しばしば**コンテキストエンジニアリング(context engineering)**と呼ばれるこの作業は、汎用AIモデルを組織のアーキテクチャ・標準・ビジネスロジックを理解する**専門家**に変えます。

開発者に必要な「ブリーフィングパケット」全体を提供することに例えられます。社内コードベース・アーキテクチャ図、Wiki・文書・スタイルガイド、運用指標・ログが含まれます。

DORA研究は、AIツールが社内データに直接アクセスするとき、AI導入のポジティブ効果が**個人の効果性とコード品質に対して統計的に有意に増幅**されることを確認しました。

## AIの視点: プロンプトエンジニアリング → コンテキストエンジニアリング

単純なプロンプトは、アシスタントに命令を1つ与えるようなものです。コンテキストエンジニアリングは、最新のAPIドキュメント・社内ポリシー・規格に合うコード片を**自動収集**し、知的なワークフローを運用する**システム**です。

- **加速**: オンボーディング・デバッグで「口伝の知識(tribal knowledge)」を即時の回答に変換、社内標準への自動検証
- **リスク**: 小さなバッチを無視するとデリバリー不安定、廃止パターンを学習すると技術的負債が増幅、アクセス制御が不十分だと機密情報が漏洩

## 実装方法（3段階）

### フェーズ1: 基盤・手動
- プロンプトエンジニアリングを**手動のコンテキストエンジニアリング**へ発展させる。
- 再利用可能な**コンテキストテンプレート／ブリーフィングパケット**のライブラリをバージョン管理とともに作る。
- 何より**社内データの品質**が先行する。存在しないデータに接続できず、誤ったデータに接続してはならない。**高品質なドキュメントがAI導入の主要な推進力**であるため、最も重要な文書から改善する。

### フェーズ2: 自動化パイロット
- 自前構築（RAGライブラリ等）か商用ツール導入を決め、**高価値のユースケース1つ**に適用する。
- 文書を丸ごとコンテキストに入れるのはしばしば**ハルシネーションを誘発**する。代わりに最も関連性の高い文脈だけを提供する。
  - **RAG（検索拡張生成）**: 最新・関連情報のみを精密に検索・提供
  - **MCP（Model Context Protocol）サーバー**: 必要な文脈だけを知的に選択・構造化して供給

### フェーズ3: スポンサーシップの獲得・拡大・運用化
- パイロットの成果でリーダーシップの投資を獲得する。
- 基盤データの問題解決と**安全な社内API**構築を通じて拡大する。

## よくある落とし穴

| 落とし穴 | 緩和策 |
|---|---|
| 品質の低い「乱雑な」社内データ | 高価値のデータソース1つでパイロット、AIで精製を支援 |
| 廃止プロジェクトまでインデックスして悪い習慣を学習 | **ゴールドスタンダードのリポジトリ**で「カリキュラム」を構成 |
| 巨大なコンテキストウィンドウへの過負荷（コンテキスト腐敗） | 量ではなく関連性。RAG/MCPで必要なチャンクだけ検索（「コンテキストハーベスティング」） |
| スーパーユーザー／共有サービスアカウントで接続 | **最小権限**の原則、ユーザー自身の資格情報で検索を動作 |

## 測定方法

**設問（5段階尺度など）**
- 文脈認識AI応答が情報探索の労力を減らした
- コードベースを理解する能力を高めた
- 検証にかかる労力が減った
- 情報探索時間が減少した

**システム指標**
- 検索イベント頻度（RAGクエリ成功回数）
- データソースのアクセス率
- AI検索レイテンシ（time-to-context）
- クエリの成功／エラー率
- 文脈豊富なプロンプトの割合
- 新規開発者のオンボーディング時間（N番目の変更を本番に届けるまで）
