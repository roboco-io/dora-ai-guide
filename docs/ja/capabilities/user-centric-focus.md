# 5. ユーザー中心

> 原文: <https://dora.dev/capabilities/user-centric-focus/>

## 定義

**ユーザー中心(User-centric focus)** は、チームがユーザーニーズを理解し、ユーザー体験を優先し、フィードバックを活用して作業の優先順位を継続的に再調整する度合いで定義されます。デザイン哲学を超えた**測定可能なケイパビリティ**であり、組織パフォーマンスを牽引します。

> **ユーザーに集中するチームは、組織パフォーマンスが40%高い。**

## AIの視点: 増幅の舵

ユーザー中心はAI時代にいっそう重要になりました。**AIは増幅器**であり、ユーザー中心というコンパスがなければ、AIのコード生成加速はチームを**より速く誤った方向へ**押し出すだけです。

- **パフォーマンスの増幅**: ユーザー中心が強いチームがAIを導入すると、効果性・チームパフォーマンスが大きくなる。ユーザー中心性が**北極星**として機能する。
- **「機能工場(feature factory)」の罠**: ユーザー中心なしにAIを導入すると、チームパフォーマンスが**むしろ害になりうる。** アウトプット（出荷機能数）に最適化されたチームは、AIで低価値ソフトウェアをより速く量産する。

## 実装方法

- **ユーザーフィードバックループを統合。** アプリ内サーベイ・直接観察セッションなど**低遅延チャネル**でフィードバックを得て、即座に優先順位の再調整に使う。AI支援チームにとってこのフィードバックは**プロンプトの精緻化**とAI出力がユーザーニーズに合うかの検証に不可欠。
- **ユーザー指標を可視化。** ダッシュボードがvelocity・デプロイ頻度しか示さなければユーザーは忘れられる。CSAT・タスク完了率・H.E.A.R.T指標を技術指標と並べて目立たせる。
- **エンジニアをユーザーリサーチに参加させる。** PM・UXリサーチャーはエンジニアとユーザーの**つながりを促進**すべきで、距離を強制してはならない。開発者がユーザーテストセッションを直接観察すると持続的な共感が生まれる。
- **スペック駆動開発(Spec-driven Development, SDD)を活用。** コードを書く前にユーザーニーズ・制約を詳細な文書(スペック)に練り上げ、それをAIエージェントの**真実の源**として、生成コードが実際の要件に縛られるようにする。

## よくある落とし穴

- **機能工場マインドセット**: 結果（ユーザー価値）ではなくアウトプット（velocity、出荷機能）を測る。AIがこれを悪化させうる。
- **履歴書駆動開発(resume-driven)**: 特定のAIモデルなど新技術を、問題解決ではなくそれ自体のために導入する「ソリューショニズム」。
- **組織サイロ**: 開発者とエンドユーザーを体系的に断絶させる「ゲートキーパー」モデルは、AI出力を検証する深い文脈を奪う。

## 測定方法

**製品パフォーマンス**: 採用率、継続率、顧客満足度。

**フィードバック統合**: ユーザーフィードバックが機能優先順位・スペック変更につながった頻度。

**チームの整合**: 以下のような記述にチームが同意する度合い
- 「ユーザーへの価値創出が私たちの焦点である」
- 「ユーザーが達成したいことを明確に理解している」
